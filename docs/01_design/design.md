# glance 設計書

作成日: 2026-11-10
状態: 初版（実装前）。リポジトリ名は glance。外販するときの製品名は別に決める（§12）。

---

## 1. 目的

管理コンソールでダッシュボードを見ながら、AI に自由文で質問すると、それに沿った集計がグラフ・表で画面に出るようにする。

- 「今月の流入数を流入元別に推移で」→ 日付×チャネルのセッション数を折れ線で出す
- 「そこから各流入の UTM ごとの実数を」→ 直前の条件を引き継ぎ、UTM 別のセッション数を表で出す
- 良かった結果はダッシュボードにピン留めし、開くたびに最新の期間で集計し直す

最初は LogiShift の GA4・GSC・Bing で使えるようにする。その後 TechShift・ConShift を足し、最終的には他社サイト向けに外販する。

## 2. 範囲

| 区分 | 内容 |
|---|---|
| 最初にやる | LogiShift の GA4・GSC・Bing の日次取得、Postgres への保存、AI による質問応答、ダッシュボード |
| 後でやる | TechShift・ConShift の追加、外販（Google ログイン、サインアップ、課金） |
| やらない（今回） | GA4 のイベント単位の生データ（BigQuery）、実売上システム（Shopify 等）との連携 |

## 3. 基本方針

1. **質問時に外部 API を呼ばない。** 1日1回のバッチで Postgres に溜めた日次データだけで答える。
2. **GA4 は「日付×主要項目」の日次集計を、そのまま取得する。** 取得時には絞り込まない。イベント単位の生データは持たない。
3. **ボットなどの除外は画面（SQL）で行う。** 除外に使う列（言語、ランディングページ）を各テーブルに持たせ、除外のオン/オフを画面で切り替える。
4. **画面の数字はすべて SQL の結果から描画する。** AI は数字を作らない。
5. **AI は SQL を書かない。** 決められた指標・軸・期間から「問い合わせ指定」を選び、サーバーが SQL に変換する。
6. **最初から複数サイト・複数顧客を前提にする。** 全テーブルにサイト ID を持たせ、DB の行単位の権限設定（行レベルセキュリティ）で分離する。
7. **サイト固有の設定はコードに書かない。** 除外設定とデータ注記はサイトごとの設定として持つ。

## 4. 全体構成

```
[1日1回のバッチ]                  [API サーバー]                          [管理コンソール]
GA4 Data API ─┐                                                          質問
GSC API      ─┼→ そのまま取得 → Postgres ← SQL（除外を適用）← 問い合わせ指定 ← Claude ←
Bing API     ─┘                 (日次テーブル)  → 結果 → グラフ・表 + AI の解説
```

| 構成要素 | 役割 |
|---|---|
| バッチ | 各 API から日次データを取得し、Postgres に上書き保存する |
| Postgres | 日次テーブル、サイト設定、取得ログ、保存したダッシュボード、質問履歴 |
| API サーバー | 問い合わせ指定の検証と SQL 変換（除外の適用を含む）、Claude の呼び出し |
| 管理コンソール | チャット、結果カード（グラフ・表）、ダッシュボード、サイト設定 |

技術スタック（案。LeadHub と揃える）: Python（uv、FastAPI、SQLAlchemy + Alembic）、Next.js、PostgreSQL、Claude API（anthropic Python SDK）。ホスティング先は未定（§12）。

## 5. データの取得（バッチ）

### 5.1 共通ルール

- 1日1回、早朝に動かす。
- **毎回、直近7日分を取り直して上書きする。** GA4・GSC・Bing とも直近2〜3日の数字は確定していないため、これ1つのルールで全部まかなう。
- 取得ごとに取得ログ（サイト・ソース・テーブル・対象期間・行数・`(other)` 行数・成否）を残す。画面には「◯月◯日までのデータ」と出す。
- 失敗した日は、取得ログで欠けている日を判定し、次回に取り直す。
- 日付は各 API が返すまま保存する。GA4 はプロパティのタイムゾーン、GSC は米国太平洋時間。日単位で並べると1日ずれることがある旨を画面に注記する。

### 5.2 GA4

- **API**: GA4 Data API（`runReport`）。
- **1回の取得の上限**: 軸（ディメンション）9個・指標10個。絞り込みに使う項目も軸の9個に数えられる（付録 A）。取得時には絞り込まないので、9個すべてを表の軸に使える。
- **認証**: LogiShift は既存のサービスアカウント（logishift リポジトリの `GOOGLE_ANALYTICS_SERVICE_ACCOUNT_KEY`）。外販時は顧客の Google ログイン（OAuth、`analytics.readonly`）。
- **利用上限**: 標準プロパティは1日20万トークン。実測では1回の取得で数〜100トークン程度で、日次バッチでは問題にならない。
- **`(other)`**: 行が多い表では、GA4 が一部の行を `(other)` にまとめることがある。LogiShift の1日分ではどの表でも発生しなかった。発生したら取得ログに記録し、画面で注記する。

### 5.3 GSC

- **API**: Search Console API（`searchanalytics.query`）、検索タイプは `web`。確定データのみを取り、直近7日の取り直しで追いつく。
- **上限**: 1日あたり5万行（検索タイプごと）。1回の取得は2.5万行までで、`startRow` でページングする。
- **伏せられたクエリ**: Google が伏せたクエリは、クエリを含む表には入らない。合計はページ表・サイト表から出す。
- **少ないクエリの整理**: 翌月8日以降（月の数字が確定した後）に、その月の表示回数がクエリ単位で10回未満のクエリを、クエリ表から削除する。
  - クエリ単位で数えるので、5回ずつ3ページに出たクエリ（合計15回）は残る。
  - 合計はページ表・サイト表から出すので、影響しない。
  - 消した分も、16ヶ月以内なら API から取り直せる。
- **過去分**: 16ヶ月前まで。それより古い分は API からも消える。

### 5.4 Bing

- **API**: Bing Webmaster API。認証は API キー。
  - `GetRankAndTrafficStats`: サイト全体の日次（約98日分）
  - `GetPageStats`: ページ別の週次。**上位100ページのみ**、13週分
  - `GetCrawlStats`: 日次のクロール数・インデックス数・被リンク数
- **使わないもの**: `GetUrlTrafficInfo`（実際には表示回数があるページにも 0 を返す）。
- **後回し**: `GetQueryStats`・`GetPageQueryStats` は未検証。確かめてから足す。
- **遡れない**: 日次で保存しないと消えていくため、最初に動かす。
- **データの癖**: 曜日差が大きい（金・土が低い）。インデックス数はその日の在庫数で、合計してはいけない。

### 5.5 初回の取り込み（過去分）

| ソース | 範囲 |
|---|---|
| GA4 | プロパティ作成以降の全期間（日ごとに分けて取る） |
| GSC | 16ヶ月前まで |
| Bing | API が返す範囲（日次は約98日、ページ別は13週） |

## 6. データベース

### 6.1 レコードの単位

**1行＝「1日 × 軸の値の組み合わせ1通り」の集計値。** 1セッションや1イベントで1行ではない。セッション ID・ユーザー ID は持たないので、この粒度より細かくはできない。

軸を1つ足すと、その値ごとに行が分かれる（合計は変わらず、1行あたりの数字が小さくなり、行数が増える）。

**別々に取得した表は、一般にはつなげない。** 例えば「デバイス別」と「新規/リピーター別」を別々に取っても、「モバイル×リピーター」はわからない（付録 A）。つなげるのは、片方の値がキーで1つに決まる場合だけ（例: チャネルは「参照元×メディア×キャンペーン」で決まる）。

### 6.2 共通テーブル

| テーブル | 内容 |
|---|---|
| `tenants` | 顧客 |
| `sites` | サイト（顧客 ID、名前、タイムゾーン、GA4 プロパティ ID、GSC サイト URL、Bing サイト URL） |
| `connections` | データ接続（サイト ID、ソース、認証方式、認証情報（暗号化）） |
| `site_exclusions` | 除外設定（サイト ID、名前、対象の列、条件、値、既定でオンか）。§7.4 |
| `data_notes` | データ注記（サイト ID、対象のソース・指標・軸、期間、注記文）。結果が該当期間・項目に触れるとき、グラフの下に表示する |
| `sync_runs` | 取得ログ（§5.1） |
| `saved_queries` | ダッシュボードにピン留めした問い合わせ指定（タイトル、指定 JSON、除外のオン/オフ、並び順） |
| `conversations` / `messages` | 質問履歴（質問、問い合わせ指定、AI の解説、トークン数） |

すべてのデータテーブルにサイト ID を持たせ、行レベルセキュリティで顧客ごとに分離する。

### 6.3 GA4 テーブル

**共通指標（9個）**: セッション、エンゲージのあったセッション、PV、エンゲージメント時間、キーイベント、売上、購入数、カート投入数、チェックアウト開始数。ECでないサイトでは EC の指標が 0 になるだけ。

| テーブル | 軸 | 指標 |
|---|---|---|
| `ga4_utm_device` | 日付、参照元、メディア、キャンペーン、UTM term、UTM content、デバイス、言語、ランディングページ | 共通指標 |
| `ga4_utm_visitor` | 日付、参照元、メディア、キャンペーン、UTM term、UTM content、新規/リピーター、言語、ランディングページ | 共通指標 |
| `ga4_channel_map` | 参照元、メディア、キャンペーン → チャネル | （対応表） |
| `ga4_audience` | 日付、チャネル、デバイス、新規/リピーター、国、地域、言語、ランディングページ | 共通指標 |
| `ga4_events` | 日付、イベント名、チャネル、デバイス、言語、ランディングページ | イベント数 |
| `ga4_totals` | 日付、言語、ランディングページ | 共通指標（全体の数字はここから出す） |
| `ga4_pages` | 日付、ページ、言語 | PV、エンゲージメント時間 |
| `ga4_items` | 日付、商品 ID、商品名、商品カテゴリ | 閲覧数、カート投入数、購入数、商品売上 |
| `ga4_users` | 期間の単位（日・週・月）、期間の開始日、内訳の種類、内訳の値、言語 | ユーザー数、新規ユーザー数、アクティブユーザー数 |

- **UTM の表は2枚に分ける。** 言語・ランディングページを足すと1枚では10項目になり、上限の9を超えるため。見られないのは「UTM×デバイス×新規/リピーター」の3つ同時だけ。
- **チャネルは UTM の表に持たず、`ga4_channel_map` でつなぐ。** チャネルは「参照元×メディア×キャンペーン」で1つに決まる（2026-08-01〜11-08 の LogiShift では182通りすべてで1つ。付録 A）。毎回の取得で対応表も更新し、1つの組が複数のチャネルになったら取得ログに記録する。
- **閲覧ページは `ga4_pages` だけに持たせる。** セッションの表に閲覧ページを入れると、1セッションで3ページ見れば3行に1ずつ入り、セッション数が二重に数えられるため。ランディングページはセッションの表に持たせる。
- **`ga4_users` の内訳の種類**: 全体、チャネル、デバイス、新規/リピーター、国。
  - 毎回、日は直近7日、週（月曜始まり）は今週途中と先週、月は今月途中と先月を取り直す。
  - ランディングページは持たない。ユーザー数はランディングページ別に足せないため。幽霊セッションの除外がユーザー数に与える影響は小さい（11/5: 1,336 → 1,318）。
- **商品の軸**は、組み合わせられる指標が GA4 側で制限されているため、流入元とは組み合わせない。
- 経路の分析（「このページから入った人が次に何を見たか」）は集計値では出せない。BigQuery の範囲（§2）。
- GA4 の項目名との対応は付録 B。

### 6.4 GSC テーブル

| テーブル | 軸 | 指標 |
|---|---|---|
| `gsc_query_page` | 日付、クエリ、ページ | クリック、表示回数、掲載順位 |
| `gsc_page` | 日付、ページ、デバイス | 同上 |
| `gsc_site` | 日付、国、デバイス | 同上 |

- クエリの表にはデバイスを持たない（行数を抑えるため）。デバイス別はページ表・サイト表で見る。
- クエリの表は月ごとに整理する（§5.3）。
- 掲載順位は「順位×表示回数」も保存し、集計では表示回数の重みつき平均にする。

### 6.5 Bing テーブル

| テーブル | 軸 | 指標 |
|---|---|---|
| `bing_site_daily` | 日付 | 表示回数、クリック |
| `bing_page_weekly` | 週、ページ（上位100ページのみ） | 表示回数、クリック、平均掲載順位 |
| `bing_crawl_daily` | 日付 | クロール数、インデックス数、被リンク数、クロールエラー |

Bing からの訪問数は GA4（参照元 = bing）で全部取れる。Bing 側で見るのは表示回数・順位・クロール。

### 6.6 集計のルール

| 種類 | 指標 | 集計方法 |
|---|---|---|
| 合計できる | セッション、PV、エンゲージのあったセッション、キーイベント、売上、購入数、カート投入数、チェックアウト開始数、イベント数、GSC・Bing のクリックと表示回数 | 合計 |
| 計算する | エンゲージメント率 | エンゲージのあったセッション ÷ セッション |
| 計算する | セッションあたりエンゲージメント時間 | エンゲージメント時間 ÷ セッション |
| 計算する | CTR | クリック ÷ 表示回数 |
| 計算する | GSC の掲載順位 | Σ(順位×表示回数) ÷ Σ表示回数 |
| 足し算できない | ユーザー数、新規ユーザー数、アクティブユーザー数 | `ga4_users` の日・週・月単位でのみ出す。任意の期間はセッション数で代わりに見せる |
| 足し算できない | Bing のインデックス数・被リンク数 | 期間末の値 |

**全体の数字は、内訳の表ではなく `ga4_totals` から出す。** 1つのセッションが複数の内訳に数えられることがあり、内訳の表を足すと全体より多くなる（LogiShift の 2026-11-05: 全体 1,080 に対し、地域別の合計は 1,152、+6.7%）。`ga4_totals` もランディングページ別に持つため、GA4 から直接取った全体よりわずかに多くなる（同日 +0.5%）。この差は画面に注記する。

### 6.7 行数の見込み（LogiShift）

| 表 | 1日の行数 |
|---|---|
| GA4 のセッションの表（ランディングページつき） | 各1,000前後（推定。ランディングページ別の表が 11/5 に719行） |
| GA4 ページ | 600〜1,000（11/5 の実測 581行） |
| GSC クエリ×ページ | 未測定。月ごとの整理で減らす |
| Bing | 数行〜100行 |

LogiShift の規模なら Postgres の性能は問題にならない（「サイト ID＋日付」の索引で十分）。容量は GSC を中心に数GB規模になりうるので、ホスティング先を選ぶ条件に入れる。行数は実装の最初に実測する。

## 7. 問い合わせ指定（AI と SQL の間）

### 7.1 指定の形

```json
{
  "metrics": ["sessions"],
  "dimensions": ["date", "channel"],
  "filters": [{"dimension": "channel", "op": "in", "values": ["Organic Search", "Referral"]}],
  "period": {"preset": "this_month"},
  "compare": "previous_period",
  "sort": {"metric": "sessions", "order": "desc"},
  "limit": 50
}
```

- `metrics` / `dimensions` は §6.6・付録 B の一覧の ID から選ぶ。時間の軸は `date` / `week` / `month`。
- `period`: `this_month` / `last_month` / `this_week` / `last_week` / `last_7_days` / `last_28_days`、または `{"start": "...", "end": "..."}`。週は月曜始まり。
- `compare`: `previous_period` / `previous_year` / なし。
- `exclusions`（省略可）: 適用する除外設定の ID の一覧。省略したらサイトの既定を使う。AI は、利用者が「ボットも含めて」のように頼んだときだけ指定する。
- サイト ID は指定に含めない。サーバーがログイン中のサイトから付ける。

### 7.2 サーバーの処理

1. **検証する。** 指標・軸が一覧にあるか、1つのテーブルにそろうかを確かめる。そろわなければ、出せない理由と、出せる組み合わせを返す。
2. **テーブルを選ぶ。** 指定の軸をすべて含むテーブルのうち、軸の数が最も少ないものを使う。
   - 軸が日付だけなら `ga4_totals`。
   - UTM の表でチャネルが要るときは、`ga4_channel_map` でつなぐ。
   - ユーザー数は `ga4_users` のみ。期間が日・週・月の単位に合わなければエラーにする。
3. **SQL を組み立てる。**
   - パラメータ付きで組み立て、サイト ID の条件を必ず付ける。DB 側でも行レベルセキュリティで二重に守る。
   - 除外設定を `WHERE` の条件として加える。対象の列がない表（例: ランディングページのない `ga4_pages`）では、その除外は適用されない。そのことを結果に含める。
4. **比較する。** `compare` があれば比較期間でも同じ集計をし、差と増減率をサーバーで計算する。
5. **返す。** 行、条件（期間・軸・適用した除外）、該当するデータ注記、データの鮮度を返す。

### 7.3 表示のルール

- 日付軸があれば折れ線グラフ。内訳が多いときは上位5件と「その他」にまとめる（表には全件出す）。
- 日付軸がなければ表と横棒グラフ（上位20件）。
- グラフの下に、条件・適用した除外・データ注記・データの鮮度を必ず出す。

### 7.4 除外設定

- サイトごとに `site_exclusions` で定義する。条件に使えるのは、各表が持つ列（言語、ランディングページ、国など）。
- それぞれに「既定でオンか」を持たせる。結果カードでオン/オフを切り替えられ、ピン留めすると切り替えた状態も保存する。
- すべてオフにすると、GA4 の画面とほぼ同じ数字になる（§6.6 の差を除く）。
- 外販先の顧客は、除外設定なしで始める。

## 8. AI の役割

### 8.1 モデルと呼び出し方

- **モデル**: `claude-opus-5-5`（Claude API、Messages API）。
  - `effort` は明示する（このモデルの既定は `medium`）。評価用の質問セット（§8.4）で `low` と `medium` を比べて決める。
- **ツール**: `run_query` を1つだけ定義する。
  - 入力は問い合わせ指定（§7.1）。`strict: true` にし、指標・軸の ID は列挙型（enum）にする。
  - このモデルでは特定ツールの強制指定（`tool_choice` の `any` / `tool`）が使えない。`auto` のまま、システムプロンプトで「数字が要る質問には必ず `run_query` を使う」と指示する。
- 1回の質問で `run_query` を複数回呼んでよい（比較など）。上限は5回。
- **AI に返す結果**: 上位30行、合計、条件、データ注記。画面には全行を出す。
- **出せない組み合わせのとき**: エラー（`is_error`）として、出せない理由と出せる組み合わせを返す。AI は指定を言い換えるか、「この組み合わせは出せません」と答える。

### 8.2 プロンプト

- **システムプロンプト（固定）**
  - 役割
  - 指標・軸の一覧（日本語名、意味、どのテーブルにあるか）
  - 解説のルール（§8.3）
  - サイトの常時の注意（データ注記のうち期間の終わりがないもの）、除外設定の一覧
- 固定部分はプロンプトキャッシュを使う。今日の日付など変わる情報は、キャッシュの後ろ（ユーザーメッセージ側）に置く。
- **会話履歴**: 直前の問い合わせ指定を含めて送る。これで「そこから UTM ごとに」のような続きの質問に答えられる。

### 8.3 解説のルール

- 数字は、ツールの結果に出ている値だけを書く。増減率などの計算はせず、`compare` で出す。
- 原因は断定しない。「〜の可能性がある」と書く。
- 結果にデータ注記があれば触れる。
- 出せない質問には推測で答えない。何なら出せるかを示す。

### 8.4 精度の確かめ方

- **評価用の質問を15問程度用意する。** 各問は「質問文」と「期待する問い合わせ指定」の組にする。
- プロンプト・指標一覧・モデル・`effort` を変えたら、全問を流して確かめる。
- 入れる質問の例:
  - 今月の流入元別推移
  - UTM 別の実数（続きの質問）
  - 国別・新規/リピーター別
  - ボットを含めた数字（除外の切り替え）
  - GSC のクエリ上位
  - Bing の表示回数の推移
  - 前月比
  - 出せない質問（UTM×デバイス×新規/リピーター、商品×流入元、任意期間のユーザー数）
- 質問ごとのトークン数を `messages` に保存し、外販時の料金設計に使う。

## 9. 管理コンソール（画面）

- **チャット**: 質問すると、回答として結果カードと AI の解説が出る。結果カードには、グラフ・表、条件、適用した除外、データ注記、データの鮮度が入る。
- **除外の切り替え**: 結果カードごとに、除外設定のオン/オフを切り替えられる。
- **ピン留め**: 結果カードの「ピン留め」で、問い合わせ指定と除外の状態を `saved_queries` に保存する。
- **ダッシュボード**: ピン留めしたカードを並べる。開くたびに DB から集計し直す（「今月」などの相対期間はその日基準で解釈）。外部 API は呼ばない。
- **サイト設定**: 除外設定（既定のオン/オフ）とデータ注記を編集する。
- **サイト切り替え**: 複数サイトになったら追加する。
- **ログイン**: 最初は自分だけが使う前提で簡易な方式にする（§12）。

## 11. LogiShift の初期設定

### 11.1 除外設定（`site_exclusions`、どちらも既定でオン）

| 名前 | 条件 | 理由 |
|---|---|---|
| ボット | 言語が `Japanese` 以外を除く | GA4 は既知のボットを自動で除くが、LogiShift に来ているボットは対象外。言語が日本語以外のユーザーが約3割（10/6〜11/5）。中国語のユーザーは全員1PV・平均12秒（11/5） |
| ランディングページなし | ランディングページが `(not set)` のセッションを除く | ページを見ていないセッション。gtag.js の頃からセッションの約1割あった GA4 共通の現象で、Zaraz への切り替え後は11.5% |

### 11.2 データ注記（`data_notes`）

| 対象 | 期間 | 注記 |
|---|---|---|
| GA4 国・地域 | 2026-09-26〜 | 信頼できない。日本語ユーザーの PV の22%が米国と判定されている（Zaraz の IP を隠す設定が原因とみられる。未確認） |
| GA4 ユーザー数・新規/リピーター | 2026-09-26 をまたぐ期間 | Zaraz への切り替えでユーザー ID が振り直され、全員が新規扱いになった。この日をまたぐ比較はできない |
| GA4 イベント（scroll） | 2026-09-26〜 | 拡張計測の scroll が Zaraz への切り替え後 0 になっている |
| Bing 日次 | 常時 | 曜日差が大きい（金・土が低い）。直近2〜3日は確定していない |

## 13. 進め方

1. **DB と Bing・GSC のバッチを作り、過去分を取り込む。** Bing は遡れず、GSC は16ヶ月で消えるため最初にやる。
2. **GA4 のバッチを作り、過去分を取り込む。**
3. **問い合わせ指定から SQL への変換（サーバー）と、評価用の質問セットを作る。**
4. **管理コンソールを作る。** 結果カード、チャット、ダッシュボード、サイト設定。
5. **TechShift・ConShift を追加する。** 2つめのサイトでサイト間の分離を確かめる。
6. **外販の準備をする**（§10 の「後でやる」）。

# glance DB 設計

日次データ・設定・会話履歴を入れる Postgres のテーブルと、集計のルールの設計。データの取り方は [data_sources.md](data_sources.md)、集計の指定と SQL への変換は [api_design.md](api_design.md)。

---

## 1. レコードの単位

**1行＝「1日 × 軸の値の組み合わせ1通り」の集計値。** 1セッションや1イベントで1行ではない。セッション ID・ユーザー ID は持たないので、この粒度より細かくはできない。

軸を1つ足すと、その値ごとに行が分かれる（合計は変わらず、1行あたりの数字が小さくなり、行数が増える）。

**別々に取得した表は、一般にはつなげない。** 例えば「デバイス別」と「新規/リピーター別」を別々に取っても、「モバイル×リピーター」はわからない（付録 A）。つなげるのは、片方の値がキーで1つに決まる場合だけ（例: チャネルは「参照元×メディア×キャンペーン」で決まる）。

## 2. 共通テーブル

| テーブル | 内容 |
|---|---|
| `tenants` | 顧客。1番目の段階では自社の1つだけで、マイグレーションで作る |
| `users` | 利用者（顧客 ID、Google のアカウント ID（`sub`）、メールアドレス、更新トークン（暗号化）、許可された範囲、最後にログインした日時）。初めてログインしたときに作る（[technical_design.md](technical_design.md) §4） |
| `sessions` | ログインのセッション（セッション ID のハッシュ、利用者 ID、期限） |
| `sites` | サイト（顧客 ID、名前、並び順、タイムゾーン、GA4 プロパティ ID） |
| `connections` | データ接続（サイト ID、ソース、紐づけ先（`target`。Search Console・Bing のサイトの URL。GA4 はサイトのプロパティ ID を使うので空）、認証方式、利用者 ID（Google ログインのとき。その利用者の更新トークンで API を呼ぶ）、Bing のキー ID（Bing のとき。どのキーで API を呼ぶか。使っているキーは消せない））。ソースごとに1行で、行があれば紐づけている。紐づけを外すと消す。紐づけ先を1か所で持つため、`sites` には持たない（2026-11-28 コードレビューの対応） |
| `sitemap_urls` | サイトマップに載っている URL（サイト ID、パス）。取り込みのたびに入れ替える（読めなければ前のまま）。検索に出たページと突き合わせて、インデックスの目安にする（[data_sources.md](data_sources.md) §3） |
| `bing_keys` | Bing の API キー（顧客 ID、名前、キー（暗号化）、末尾4文字）。顧客ごとに複数持て、サイトごとにどれを使うか選ぶ（2026-11-27 利用者の決定）。キーそのものは画面に出さず、末尾4文字だけを出す |
| `site_exclusions` | 除外設定（サイト ID、名前、対象の列、条件、値、既定でオンか）。[api_design.md](api_design.md) の除外設定 |
| `data_notes` | データ注記（サイト ID、対象のソース・指標・軸、期間、注記文）。結果が該当期間・項目に触れるとき、グラフの下に表示する |
| `sync_runs` | 取得ログ（[data_sources.md](data_sources.md) の共通ルール）。サイト・ソース・表・取った先（`target`）・対象期間・行数・成否。取った先は、紐づけ先を変えたときに前の先の数字を消すのに使う。1回の取り込みで約40行増えるが、1年で1万行ほどなので消さない |
| `saved_queries` | ダッシュボードにピン留めした問い合わせ指定（タイトル、指定 JSON、除外のオン/オフ、並び順） |
| `conversations` / `messages` | 会話履歴。Gemini とやり取りした内容（利用者の質問、モデルの応答、関数呼び出しとその結果）を加工せずに保存する。次の質問ではここから会話を組み立てて送る（[ai_query_design.md](ai_query_design.md)）。トークン数も記録する |

すべてのデータテーブルにサイト ID を持たせる。紐づけを外しても、取り込んだデータは残す（つなぎ直せば続きから取り込む）。サイトを削除したときは、そのサイトのデータも消す（Bing の過去分は取り直せないので、削除の確認で伝える。2026-11-27 利用者の決定）。顧客ごとの分離（データの分け方・権限）は別途設計する。

1番目の段階（リアルタイム画面）で作るのは、`tenants`・`users`・`sessions`・`sites`・`connections` の5つ。リアルタイムの結果は入れない（[data_sources.md](data_sources.md) §5）。

## 3. GA4 テーブル

**共通指標（9個）**: セッション、エンゲージのあったセッション、PV、エンゲージメント時間、キーイベント、売上、購入数、カート投入数、チェックアウト開始数。EC でないサイトでは EC の指標が 0 になるだけ。

| テーブル | 軸 | 指標 |
|---|---|---|
| `ga4_utm_device` | 日付、参照元、メディア、キャンペーン、UTM term、UTM content、デバイス、言語、ランディングページ | 共通指標 |
| `ga4_utm_visitor` | 日付、参照元、メディア、キャンペーン、UTM term、UTM content、新規/リピーター、言語、ランディングページ | 共通指標 |
| `ga4_channel_map` | 参照元、メディア、キャンペーン → チャネル | （対応表） |
| `ga4_audience` | 日付、チャネル、デバイス、新規/リピーター、国、地域、言語、ランディングページ | 共通指標 |
| `ga4_events` | 日付、イベント名、チャネル、デバイス、言語、ランディングページ | イベント数 |
| `ga4_totals` | 日付、言語、ランディングページ | 共通指標（全体の数字はここから出す） |
| `ga4_pages` | 日付、ページ、ページタイトル、言語 | PV、エンゲージメント時間 |
| `ga4_items` | 日付、商品 ID、商品名、商品カテゴリ | 閲覧数、カート投入数、購入数、商品売上 |
| `ga4_users` | 期間の単位（日・週・月）、期間の開始日、内訳の種類、内訳の値、言語 | ユーザー数、新規ユーザー数、アクティブユーザー数 |
| `ga4_hourly` | 日時（時）、チャネル、参照元、メディア、キャンペーン、デバイス、言語、ランディングページなしか | 共通指標（**1時間単位。直近31日だけ持つ**） |

- **UTM の表は2枚に分ける。** 言語・ランディングページを足すと1枚では10項目になり、上限の9を超えるため。
- **1つの表にそろう組み合わせしか出せない。** 主な出せない組み合わせ:
  - UTM×デバイス×新規/リピーター（3つ同時）
  - UTM×国・地域（UTM の表は国を持たず、`ga4_audience` は UTM を持たない。チャネル×国・地域は出せる）
  - 閲覧ページ×流入元・デバイス・新規/リピーター・国（`ga4_pages` は日付・ページ・ページタイトル・言語だけ）。流入元別に見られるのは、ランディングページ（入口）ごとのセッション数まで
  - イベント×UTM・国・新規/リピーター（`ga4_events` はチャネル・デバイス・言語・ランディングページだけ）
  - 商品×商品以外の軸（`ga4_items` は商品の軸だけ）
  - ユーザー数×ランディングページ・UTM（`ga4_users` の内訳は全体・チャネル・デバイス・新規/リピーター・国だけ）
- **チャネルは UTM の表に持たず、`ga4_channel_map` でつなぐ。** チャネルは「参照元×メディア×キャンペーン」で1つに決まる（2026-08-01〜11-08 の LogiShift では182通りすべてで1つ。付録 A）。毎回の取得で対応表も更新し、1つの組が複数のチャネルになったら取得ログに記録する。対応表の持ち方は未決（§9）。
- **閲覧ページは `ga4_pages` だけに持たせる。** セッションの表に閲覧ページを入れると、1セッションで3ページ見れば3行に1ずつ入り、セッション数が二重に数えられるため。ランディングページはセッションの表に持たせる。
- **ページタイトルは `ga4_pages` に持たせる。** パスごとに、最後に出た日のタイトルをそのページの今のタイトルとする。ランディングページ（GA4）や GSC・Bing のページにも、パスでつないでタイトルを付ける。`ga4_pages` に一度も出ていないパスは、タイトルなし（パスだけ）にする。
- **`ga4_hourly`（1時間単位）**: 流入・チャネルの時間ごとの動きを見るための表（2026-11-26 利用者の決定）。
  - 持つのは直近31日だけ。過ぎた行は日次のバッチで消す。日に丸めることはしない（日次の表を別に、ずっと持っているため。時間ごとの数字を足して日を作ると、ユーザー数や時間をまたいだセッションで日次と合わなくなる）。
  - ページ・ランディングページは持たない（行が一番増えるため）。代わりに「ランディングページなしか」（はい/いいえ）を持ち、ページを見ていないセッションの除外を、日次と同じく切り替えられるようにする（[data_sources.md](data_sources.md) §2 の取り方）。
  - チャネルは直接持つ（軸が8個で上限の9に収まるため。日次の UTM の表のように対応表でつながない）。
  - ユーザー数は持たない（時間をまたいで重複し、足せないため。ユーザー数は `ga4_users` だけで出す）。
  - 見込み（推定。実装の最初に実測する）: LogiShift で1日1,000〜2,000行、31日で3〜6万行。5サイトでも30万行前後。
- **`ga4_users` の内訳の種類**: 全体、チャネル、デバイス、新規/リピーター、国。
  - 毎回、日は日次の表と同じ範囲（取得済みの最終日の3日前から今日まで。[data_sources.md](data_sources.md) §1）、週（月曜始まり）と月は、その範囲にかかる週・月（途中の今週・今月を含む）を取り直す。
  - ランディングページは持たない。ユーザー数はランディングページ別に足せないため。幽霊セッションの除外がユーザー数に与える影響は小さい（11/5: 1,336 → 1,318）。
- **商品の軸**は、組み合わせられる指標が GA4 側で制限されているため、流入元とは組み合わせない。
- 経路の分析（「このページから入った人が次に何を見たか」）は集計値では出せない。BigQuery の範囲（[overview.md](overview.md) の範囲）。
- GA4 の項目名との対応は [api_design.md](api_design.md) 付録。

## 4. GSC テーブル

| テーブル | 軸 | 指標 |
|---|---|---|
| `gsc_query_page` | 日付、クエリ、ページ | クリック、表示回数、掲載順位 |
| `gsc_page` | 日付、ページ、デバイス | 同上 |
| `gsc_site` | 日付、国、デバイス | 同上 |

- **サイト全体の数字は `gsc_site` から出す。** GSC は、ページを軸に含めるとページ単位で、含めないとサイト単位で集計する。ページ単位では、1回の検索結果に同じサイトのページが2つ出ると表示回数を2と数え（サイト単位では1）、掲載順位もページごとの順位になる（サイト単位ではそのサイトの最上位の順位）。そのためページ表の合計はサイト全体と一致しない。
- クエリの表は、伏せられたクエリと整理した少ないクエリ（[data_sources.md](data_sources.md) の GSC）を含まないので、合計はサイト全体より小さい。
- クエリの表にはデバイスを持たない（行数を抑えるため）。デバイス別はページ表・サイト表で見る。
- クエリの表は月ごとに整理する（[data_sources.md](data_sources.md) の GSC）。
- 掲載順位は「順位×表示回数」も保存し（`position_weighted`）、集計では表示回数の重みつき平均にする。
- 主キーは、サイト ID と軸の全部（`gsc_site` は日付・国・デバイス、`gsc_page` は日付・ページ・デバイス、`gsc_query_page` は日付・クエリ・ページ）。取り込みでそろえて同じ軸になった行は足し合わせる。

## 5. Bing テーブル

| テーブル | 軸 | 指標 |
|---|---|---|
| `bing_site_daily` | 日付 | 表示回数、クリック |
| `bing_page_weekly` | 週、ページ（上位100ページのみ） | 表示回数、クリック、平均掲載順位 |
| `bing_crawl_daily` | 日付 | クロール数、インデックス数、被リンク数、クロールエラー |

- **どのテーブルにも `raw`（jsonb）列を持たせ、API が返した1件をそのまま入れる。** Bing は後から取り直せないため。表の列にない項目（クロールの応答コード別の件数、クリック時の平均順位など）も、後から使える。
- Bing からの訪問数は GA4（参照元 = bing）で全部取れる。Bing 側で見るのは表示回数・順位・クロール。
- 主キーは、サイト ID と日付（ページ別は週の日付とページ）。ページ別の掲載順位は、表示されたときの平均掲載順位（`AvgImpressionPosition`）。

## 6. 集計のルール

| 種類 | 指標 | 集計方法 |
|---|---|---|
| 合計できる | セッション、PV、エンゲージのあったセッション、キーイベント、売上、購入数、カート投入数、チェックアウト開始数、イベント数、GSC・Bing のクリックと表示回数 | 合計 |
| 計算する | エンゲージメント率 | エンゲージのあったセッション ÷ セッション |
| 計算する | セッションあたりエンゲージメント時間 | エンゲージメント時間 ÷ セッション |
| 計算する | CTR | クリック ÷ 表示回数 |
| 計算する | GSC の掲載順位 | Σ(順位×表示回数) ÷ Σ表示回数 |
| 足し算できない | ユーザー数、新規ユーザー数、アクティブユーザー数 | 期間が `ga4_users` の日・週・月の単位に合うときは、その値（重複を除いた人数）。それ以外の期間は、日ごとの人数を足した延べ人数で出し、「延べ」と表示する |
| 足し算できない | Bing のインデックス数・被リンク数 | 期間末の値 |

**全体の数字は、内訳の表ではなく `ga4_totals` から出す。** 1つのセッションが複数の内訳に数えられることがあり、内訳の表を足すと全体より多くなる。`ga4_totals` もランディングページ別に持つため、GA4 から直接取った全体よりわずかに多くなる（2026-11-05: +0.5%）。この差は画面に注記する。

**国・地域の重複は、差分の行で調整する。** 国・地域は1セッションの途中で判定が変わることがあり、そのセッションは2つの行に数えられる（2026-11-05: 全体 1,080 に対し、国別の合計 1,096、地域別の合計 1,152。付録 A）。`ga4_audience` は国と地域を同じ表に持つので、国で集計しても地域の重複が混ざる。

- **取得**: `ga4_audience` を「国×地域つき」に加えて、「国まで（地域なし）」「国・地域なし」でも取得する。それ以外の軸は同じ。1日の取得が2回増える。
- **保存する調整行**（国・地域以外の軸の組み合わせごと）:
  - 国ごとの調整: 地域を `(重複調整)` とし、値は「国までの値 − その国の地域の合計」
  - 全体の調整: 国・地域を `(重複調整)` とし、値は「国・地域なしの値 − 国までの値の合計」
- **結果**: 国で集計すると、各国の値が「国まで」で取った値と一致する。どの軸で集計しても、合計が「国・地域なし」で取った値と一致する。
- 差が出るのは、重複を除いて数える指標（セッション、エンゲージのあったセッション）だけ。PV などイベントの件数を数える指標は差が 0 になる。
- 画面での出し方は [api_design.md](api_design.md) の表示のルール。

## 7. 値のそろえ方（取り込み時）

ソースごとに形が違う値は、取り込み時にそろえて保存する。指標・軸の ID と各ソースの項目名の対応は [api_design.md](api_design.md) 付録。

| 項目 | 保存する形 | GA4 | GSC | Bing |
|---|---|---|---|---|
| 日付 | 日付型（`YYYY-MM-DD`） | `date`（`YYYYMMDD`）を変換 | そのまま | `/Date(…)/` 形式を変換 |
| デバイス | GA4 の値（`desktop` / `mobile` / `tablet` など、小文字） | `deviceCategory` のまま | `DESKTOP` などを小文字に | （なし） |
| 国 | ISO 3166-1 の2文字コード（`JP`） | `countryId` | 3文字コード（`jpn`）を2文字に変換 | （なし） |
| ページ | パス（ホスト名・クエリ文字列・`#` 以降を除き、パーセントエンコードを解除） | `pagePath` / `landingPage` | 完全な URL をパスに | 完全な URL をパスに |

- 国名などの日本語名は、画面に出すときに変換する。
- GSC の URL はパーセントエンコードされた形で返る。解除してから保存しないと、GA4 のページと突き合わせられない。

## 8. 行数の見込み（LogiShift）

| 表 | 1日の行数 |
|---|---|
| GA4 のセッションの表（ランディングページつき） | 各1,000前後（推定。ランディングページ別の表が 11/5 に719行） |
| GA4 ページ | 600〜1,000（11/5 の実測 581行） |
| GSC クエリ×ページ | 未測定。月ごとの整理で減らす |
| Bing | 数行〜100行 |

LogiShift の規模なら Postgres の性能は問題にならない（「サイト ID＋日付」の索引で十分）。容量は GSC を中心に数GB規模になりうる。置き場所は LeadHub と同じ VPS の PostgreSQL（[infrastructure_design.md](infrastructure_design.md) §1・§3）。行数は実装の最初に実測する。

## 9. 未決事項

- **チャネル対応表に日付を持たせるか。** 2026-05-13 から GA4 の既定チャネルに「AI Assistant」が加わり、それより前のデータは付け替えられていない。同じ「参照元×メディア×キャンペーン」（例: `chatgpt.com / referral`）でも日付によってチャネルが違うので、日付のない対応表では過去分を GA4 と同じチャネルでつなげない。
- **対応表の更新のしかた。** 毎回の取得（取得済みの最終日の3日前から今日まで）で表を入れ替えるのか、行を足す・書き換えるだけで消さないのか。
- **データ注記の形。** GA4 の注釈のように、日付（または期間）にタイトルと説明を付けて時系列グラフに印を出す形にするか。

## 付録 A: 確認ログ（2026-11-10、LogiShift の GA4）

### 1回の取得の上限（2026-11-05 の1日分）

- 軸9個＋軸に含めない2項目（ランディングページ、言語）で絞り込み → 400 エラー。
  `Requests are limited to 9 dimensions in a nested request. Through DimensionExpression and DimensionFilter, this request is for 11 dimensions.`
- 軸7個＋同じ絞り込み → 成功。
- `(other)` 行は、試したどの表でも 0。

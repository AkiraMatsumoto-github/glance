# glance 企画・システム概要

作成日: 2026-11-10
状態: 初版（実装前）。リポジトリ名は glance。外販するときの製品名は別に決める（§8）。

このファイルには、企画（誰の何を解決するか）と、システム全体の考え方・特徴・主な構成をまとめる。各部分の詳しい設計は §7 の各ファイルに書く。

## 1. 企画

### 1.1 背景

- サイトの担当者の多くは分析の専門家ではない。管理画面で数字の推移は見られても、急に増えた・減った指標が何を意味するのか、次に何をすればよいのかまでは読み取れない。
- 変化の意味を読むには、複数のデータを組み合わせる必要がある。例えばセッションが急に減ったときは、減ったのは検索流入か（GA4）、どのページ・クエリの表示回数や順位が落ちたのか（Search Console）、インデックスから外れていないか（Bing のクロール・インデックス）を順に確かめる。これには3つの管理画面と、それぞれの操作の知識が要る。
- GA4 にはボットが混ざり、ボットによる急な増加を本当の変化と取り違えやすい。GA4 のデータフィルタは過去のデータには効かないので、ボットを除いた数字を過去にさかのぼって見るのも難しい。
- Search Console は16ヶ月、Bing は日次が約98日・ページ別が13週までしか遡れない。前年の同じ時期と比べて季節的な変化かどうかを見分けたくても、取っておかないと消える。

### 1.2 ターゲット

| 段階 | 利用者 |
|---|---|
| 最初 | 自社（LogiShift・TechShift・ConShift の運営） |
| 外販 | 分析の専門スキルがないサイトの担当者（メディア・EC・企業サイト）。数字の推移や急な変化の意味を読み取れず、打ち手につなげられていない人 |

外販のターゲットの確かめ方は未定（§8）。

### 1.3 提供する価値

1. **AI が示唆を出す。** GA4・Search Console・Bing のデータを組み合わせ、推移や急な変化などの特徴から、何が起きているか・何を意味しそうかを AI が示す。
2. **AI と会話しながら打ち手・対策につなげる。** 示唆を見て質問を重ね、どの流入元・ページ・クエリかを深掘りし、打ち手・対策まで落とし込む。
3. **示唆の根拠を数字で見せる。** 示唆の根拠になった集計を、グラフ・表で一緒に出す。数字は SQL の結果で、AI は数字を作らない。
4. **よく見る集計はダッシュボードに残す。** ピン留めした集計は、開くたびに最新の期間で集計し直す。

会話の流れの例（数字は説明のための架空のもの）:

1. AI「先週の自然検索のセッションが前の週より25%減っています。Search Console では記事 A の表示回数が半分になり、掲載順位が4位から9位に下がっています」（根拠のグラフ・表つき）
2. 利用者「記事 A 以外にも下がった記事はある？」→ AI が同じ条件で記事別に集計して示す
3. 利用者「どうすればいい？」→ AI が打ち手の候補を示す（例: 記事 A の内容を最新にする、タイトルを検索されている言葉に合わせる）

### 1.4 競合と差別化

調査日: 2026-11-10。出典は末尾。

| 競合 | できること | glance との違い |
|---|---|---|
| GA4 のインサイト（Google。GA4 の標準機能） | GA4 の指標の急な変化を自動で見つけて知らせる | GA4 のデータだけ。検索側（Search Console・Bing）と合わせた説明や、打ち手までの会話はない |
| GA4 の Analytics Advisor（Google） | GA4 の画面内で Gemini に自然文で質問し、グラフ・表・文章で答えを得る。英語のプロパティから展開（日本語の状況は要確認） | GA4 のデータが対象（連携した Search Console のデータを扱えるかは未確認）。Bing は扱わない |
| Search Console の AI 設定（Google。2025-12 発表、2026-02 から全ユーザー） | 自然文から、検索パフォーマンスレポートのフィルタ・比較を設定する | レポートの設定を作るだけで、示唆は出さない。16ヶ月より前は見られない |
| Data Studio（旧 Looker Studio）の Conversational Analytics（Google） | ダッシュボードのデータに自然文で質問する（プレビュー） | ダッシュボードを作り込む前提で、専門スキルが要る。GA4・Search Console のデータで使えるかは未確認 |
| GA4 Chat Analyst（アド・セイル） | Gemini を使い、GA4 のデータに自然文で質問すると文章・グラフで答える。複数データソースの横断は今後予定 | 現時点では GA4 だけ |
| SEMAIA（エクスチュア） | GA4 などのデータを自然文で分析するマネージドサービス（2026-06 発表） | 詳細は未確認 |
| 汎用の生成 AI ＋ API 接続（ChatGPT・Claude・Gemini に GA4・Search Console の MCP や Supermetrics をつなぐ） | 何でも聞け、示唆も出せる。質問のたびに API を呼ぶ | AI が数字を集計・転記するので、示唆の根拠がぶれうる。使いこなすには聞き方の工夫が要る。過去分を貯めない |

**glance の差別化ポイント**

1. **複数のデータを組み合わせて示唆を出す。** GA4 の変化を、Search Console（クエリ・ページ・順位）と Bing（クロール・インデックス）と突き合わせて説明する。GA4 や Search Console の AI 機能はそれぞれの製品のデータが対象で、Bing まで合わせて見ることはできない。
2. **示唆から打ち手まで、会話で進められる。** 専門知識がなくても、AI の示唆を起点に深掘りし、打ち手・対策まで進められる。
3. **示唆の根拠がぶれない。** 根拠の数字は DB の集計結果で、AI は数字を作らない。同じ問いには同じ数字が出る。
4. **見かけの変化を見分けられる。** ボットを除いた数字で見られるので、ボットによる急な増加を本当の変化と取り違えない。データを貯め続けるので、Search Console の16ヶ月や Bing の98日を超えて前年の同じ時期と比べ、季節的な変化かどうかを見分けられる。
5. **すぐ答える。** 質問のたびに外部 API を呼ばないので、答えが速く、API の上限も気にしなくてよい。

## 2. システムの考え方

1. **質問時に外部 API を呼ばない。** 1日1回のバッチで Postgres に溜めた日次データだけで答える。
2. **GA4 は「日付×主要項目」の日次集計を、そのまま取得する。** 取得時には絞り込まない。イベント単位の生データは持たない。
3. **ボットなどの除外は画面（SQL）で行う。** 除外に使う列（言語、ランディングページ）を各テーブルに持たせ、除外のオン/オフを画面で切り替える。
4. **画面の数字はすべて SQL の結果から描画する。** AI は数字を作らない。
5. **AI は SQL を書かない。** 決められた指標・軸・期間から「問い合わせ指定」を選び、サーバーが SQL に変換する。
6. **最初から複数サイトを前提にする。** 全テーブルにサイト ID を持たせる。複数顧客に対応するデータの持ち方（顧客ごとの分け方・権限）は別途設計する。
7. **サイト固有の設定はコードに書かない。** 除外設定とデータ注記はサイトごとの設定として持つ。

## 3. 主な構成

```
[1日1回のバッチ]                  [API サーバー]                          [管理コンソール]
GA4 Data API ─┐                                                          質問
GSC API      ─┼→ そのまま取得 → Postgres ← SQL（除外を適用）← 問い合わせ指定 ← Gemini ←
Bing API     ─┘                 (日次テーブル)  → 結果 → グラフ・表 + AI の解説
```

| 構成要素 | 役割 | 詳細 |
|---|---|---|
| バッチ | 各 API から日次データを取得し、Postgres に上書き保存する | [data_sources.md](data_sources.md) |
| Postgres | 日次テーブル、サイト設定、取得ログ、保存したダッシュボード、会話履歴 | [database_design.md](database_design.md) |
| API サーバー | 問い合わせ指定の検証と SQL 変換（除外の適用を含む）、Gemini の呼び出し | [api_design.md](api_design.md)・[ai_query_design.md](ai_query_design.md) |
| 管理コンソール | チャット、結果カード（グラフ・表）、ダッシュボード、サイト設定 | §4 |

技術構成（案。LeadHub と揃える）: Python（uv、FastAPI、SQLAlchemy + Alembic）、Next.js、PostgreSQL、Gemini（google-genai Python SDK、Vertex AI 経由。logishift と同じ）。詳細は技術構成のファイルで決める（§7）。

## 4. 主な機能（管理コンソール）

- **全体サマリー**: ボタンを押すと、AI が GA4・Search Console・Bing の変化から示唆をまとめて出す。示唆ごとに根拠のグラフ・表が付く。
- **チャット**: いつでも質問できる。全体サマリーの後にそのまま深掘りや打ち手の相談もできる。回答として結果カードと AI の解説が出る。結果カードには、グラフ・表、条件（実際に集計した期間を含む）、適用した除外、データ注記が入る。
- **除外の切り替え**: 結果カードごとに、除外設定のオン/オフを切り替えられる。
- **ピン留め**: 結果カードの「ピン留め」で、問い合わせ指定と除外の状態を保存する。
- **ダッシュボード**: ピン留めしたカードを並べる。開くたびに DB から集計し直す（「今月」などの相対期間はその日（日本時間）基準で解釈）。外部 API は呼ばない。
- **サイト設定**: 除外設定（既定のオン/オフ）とデータ注記を編集する。
- **サイト切り替え**: 複数サイトになったら追加する。
- **ログイン**: 最初は自分だけが使う前提で簡易な方式にする（§8）。

## 5. セキュリティ

UTM・参照元・キャンペーン名・検索クエリ・ページパスなどは、誰でも任意の文字列を入れられる（URL に `?utm_campaign=...` を付けて訪問するだけで GA4 に入る）。外部から来た値として扱う。

- **画面**: 取り込んだ値と AI の解説は、必ずエスケープして表示する。グラフの凡例・ツールチップでも HTML として描画しない。
- **AI への受け渡し**: 関数の結果に含まれる文字列はデータであり指示ではない、とシステムプロンプトで明示する。AI が使えるのは集計の関数だけで、サイト ID はサーバーが付けるため、指示文を混ぜられても他サイトのデータには届かない。
- **AI の解説の表示**: Markdown を描画する場合、画像と外部へのリンクは描画しない。外部 URL の画像を読み込ませて情報を送らせる手口を防ぐため。
- **SQL**: 問い合わせ指定から組み立てる SQL はパラメータ付きにする。
- **認証情報**: データ接続の認証情報は暗号化して保存し、鍵は DB と別の場所に置く。

## 6. 範囲と進め方

### 6.1 範囲

| 区分 | 内容 |
|---|---|
| 最初にやる | LogiShift の GA4・GSC・Bing の日次取得、Postgres への保存、AI による質問応答、ダッシュボード |
| 後でやる | TechShift・ConShift の追加、外販（下の表） |
| やらない（今回） | GA4 のイベント単位の生データ（BigQuery）、実売上システム（Shopify 等）との連携 |

### 6.2 外販に向けて

| 区分 | 内容 |
|---|---|
| 最初から入れる | 全テーブルのサイト ID、接続設定の分離、除外設定・データ注記のサイト設定化、質問ごとのトークン記録 |
| 後でやる | 複数顧客に対応するデータの持ち方（顧客ごとの分け方・権限）を別途設計する |
| 後でやる | Google ログイン（`analytics.readonly`、`webmasters.readonly`）と Google の審査（審査前は利用者100人まで）、サインアップ・課金・権限管理 |
| 後でやる | 接続時の自動チェック（EC 指標が入っているか、除外設定の提案） |
| 後でやる | `(other)` が出始めたサイトでは、ランディングページを持たない表に切り替える。顧客が増えたら表を月ごとに分割する |
| 後でやる（選択肢） | BigQuery 接続（購入までの経路・リピート購入の分析が必要な顧客向け）、実売上システムとの連携 |

### 6.3 進め方

1. **DB と Bing・GSC のバッチを作り、過去分を取り込む。** Bing は遡れず、GSC は16ヶ月で消えるため最初にやる。
2. **GA4 のバッチを作り、過去分を取り込む。**
3. **問い合わせ指定から SQL への変換（サーバー）、変化の検出、評価用の質問セットを作る。**
4. **管理コンソールを作る。** 全体サマリー、結果カード、チャット、ダッシュボード、サイト設定。
5. **TechShift・ConShift を追加する。** 2つめのサイトでサイト間の分離を確かめる。
6. **外販の準備をする**（§6.2 の「後でやる」）。

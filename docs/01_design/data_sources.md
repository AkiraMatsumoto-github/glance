# glance データ取得設計

GA4・GSC・Bing から日次データを取り込むバッチと、画面を開いたときに取る GA4 リアルタイム（§5。貯めない）の設計。取り込んだデータを入れるテーブルは [database_design.md](database_design.md)、全体像は [overview.md](overview.md)。

---

## 1. 共通ルール（日次バッチ）

- 1日1回動かす。VPS に出すまでは手元で動かし、毎日でなくてもよい（[roadmap.md](roadmap.md) §3.1）。
- **毎回、「取得済みの最終日の3日前」から今日までを取り直して上書きする**（2026-11-26 利用者の決定）。GA4・GSC・Bing とも直近2〜3日の数字は確定していないので、前回まだ確定していなかった日も取り直す。毎日動かせば数日分、間があけばその間の全部を取るので、動かさなかった日があっても埋まる。初めて取るときは、§6 の過去分を取る。
- 取得ごとに取得ログ（サイト・ソース・テーブル・対象期間・行数・`(other)` 行数・成否）を残す。画面には「◯月◯日までのデータ」と出す。
- 失敗した日は、取得ログで欠けている日を判定し、次回に取り直す。
- 日付は各 API が返す日付のまま保存する（形式は [database_design.md](database_design.md) の「値のそろえ方」でそろえる）。GA4 はプロパティのタイムゾーン、GSC は米国太平洋時間。日単位で並べると1日ずれることがある旨を画面に注記する。

## 2. GA4

- **API**: GA4 Data API（`runReport`）。
- **1回の取得の上限**: 軸（ディメンション）9個・指標10個。絞り込みに使う項目も軸の9個に数えられる（[database_design.md](database_design.md) 付録 A）。取得時には絞り込まないので、9個すべてを表の軸に使える。
- **認証**: Google ログイン（OAuth、`analytics.readonly`）でもらった更新トークン。ログインしたアカウントが見られるプロパティから選んでサイトに紐づける（[infrastructure_design.md](infrastructure_design.md) §5）。自社のサイトも外販の顧客も同じ方式で、サービスアカウントは使わない。
- **利用上限**: 標準プロパティは1日20万トークン。実測では1回の取得で数〜100トークン程度で、日次バッチでは問題にならない。
- **`(other)`**: 行が多い表では、GA4 が一部の行を `(other)` にまとめることがある。LogiShift の1日分ではどの表でも発生しなかった。発生したら取得ログに記録し、画面で注記する。

### 2.1 1時間単位（`ga4_hourly`）

- **日時の軸**: 日次の表の `date` の代わりに `dateHour`（YYYYMMDDHH。プロパティのタイムゾーン）を使う。軸の数は増えない。
- **ランディングページなしか**: 同じ期間を2回に分けて取る（`landingPage` が `(not set)` のものと、それ以外）。取得時の絞り込みはしない方針（[overview.md](overview.md) §2）の例外で、ランディングページの数だけ行を増やさずに、除外の切り替えに要る印を持つため。絞り込みに使う `landingPage` も軸の9個に数えるが、8個で収まる。
- **いつ取るか**
  - 日次のバッチで、ほかの表と同じ範囲（§1。取得済みの最終日の3日前から今日まで）を取り直す。
  - 今日の分は自動では取らない（2026-11-26 利用者の決定）。1時間単位の数字を出す画面（結果カード・ダッシュボード）の「今日の分を取り直す」ボタンを押したときだけ、そのサイトの今日と昨日の分を取って入れ直す。取り直した時刻を取得ログに残し、画面に「◯時◯分に取り込んだデータ」と出す。
  - GA4 の当日の数字は遅れて入る（数時間ほど）。ボタンを押しても、直近の数時間は少なめに出ることがある。画面に注記する。
- **消す**: 日次のバッチで、31日より前の行を消す。

## 3. GSC

- **API**: Search Console API（`searchanalytics.query`）、検索タイプは `web`。確定データのみを取り、§1 の取り直しで追いつく。
- **サイトへの紐づけ**: ログインしたアカウントが見られるサイトの一覧（`sites.list`）から選ぶ（[screen_design.md](screen_design.md) §4）。GA4 のプロパティを追加するときに、そのプロパティのウェブのデータストリームの URL（Admin API の `properties.dataStreams.list`）と同じドメインのサイトを選んでおく。ドメインのプロパティ（`sc-domain:`）があればそれを選ぶ（サブドメインと http/https を全部含み、GA4 のサイト全体と数字が合いやすいため）。なければ、同じホストの URL のプロパティが1つだけあるときにそれを選ぶ（2026-11-27 利用者の決定）。
- **認証**: GA4 と同じ Google ログイン（`webmasters.readonly`）。
- **上限**: 1日あたり5万行（検索タイプごと）。1回の取得は2.5万行までで、`startRow` でページングする。
- **伏せられたクエリ**: Google が伏せたクエリは、クエリを含む表には入らない。そのためクエリ表の合計はサイト全体より小さい。サイト全体の数字は `gsc_site` から出す（[database_design.md](database_design.md) の GSC テーブル）。
- **少ないクエリの整理**: 翌月8日以降（月の数字が確定した後）に、その月の表示回数がクエリ単位で10回未満のクエリを、クエリ表から削除する。
  - クエリ単位で数えるので、5回ずつ3ページに出たクエリ（合計15回）は残る。
  - サイト全体の数字は `gsc_site` から出すので、影響しない。
  - 消した分も、16ヶ月以内なら API から取り直せる。
- **過去分**: 16ヶ月前まで。それより古い分は API からも消える。
- **インデックス状況は API に無い**（管理画面の「ページのインデックス登録」の数）。URL 検査 API は1つの URL ずつで1日2,000件まで、サイトマップ API のインデックス数の項目は廃止されている。そこで、取り込みのときに Search Console に登録したサイトマップ（`sitemaps.list`）を読んで URL を `sitemap_urls` に入れ、検索に出たページ（`gsc_page` の imp 1回以上）と突き合わせて目安にする（2026-11-28 利用者の決定。[screen_design.md](screen_design.md) §7）。サイトマップの索引（sitemapindex）は中をたどり、.gz も読む。ファイル数500・URL 20万・1ファイル50MB を上限にする。紐づけたサイトのドメインの外は読まない（転送先も確かめる）。読めなければ前のままにし、取得ログに残す。
  - 2026-11-28 に手元で読んだ: LogiShift 3,377・TechShift 1,150・FinShift 46・LeadHub 42,377 URL。ConShift は、紐づけたプロパティ（`https://conshift.net/`）にサイトマップが登録されていなかったので、利用者が登録した（2026-11-28 に 867 URL を読んだ）

## 4. Bing

- **API**: Bing Webmaster API。
- **認証**: API キー（2026-11-26 決定。OAuth 2.0 は外販の準備のときに足す）。
  - キーは Bing Webmaster Tools の「設定 → API アクセス」で作る。サイトごとではなく利用者ごとに1つで、その人が確認済みのサイトすべてに使える。Glance の Google ログインのトークンでは呼べない（Bing Webmaster Tools に Google アカウントでログインしていても同じ）。
  - サイト設定でキーを1回入れると、そのキーで見られる Bing のサイトの一覧から、各サイトに紐づけられる（[screen_design.md](screen_design.md) §4）。Bing のアカウントが分かれていれば、キーはアカウントの数だけ入れる。キーには名前を付け、サイトごとにどのキーを使うか選ぶ（2026-11-27 利用者の決定。サイトを別々に売ることがあり、Bing のアカウントが分かれうるため）。
  - キーは暗号化して顧客ごとに `bing_keys` に入れ、各サイトの接続設定（`connections`）はどのキーを使うかを持つ。キーを入れ直すと、そのキーを使う全サイトに効く。保存したキーは画面に出さず、末尾4文字だけを出す（2026-11-27 利用者の決定）。保存するときに `GetUserSites` を呼び、使えるキーかを確かめる。
  - `GetRankAndTrafficStats`: サイト全体の日次。2026-11-27 に取ったら、古いサイトは243日分（2026-03-28〜）返った（設計の時点の見込みは約98日）
  - `GetPageStats`: ページ別の週次。**各週の上位100ページのみ**。2026-11-27 は34週分（2026-04-03〜）返った。週の日付は金曜日
  - `GetCrawlStats`: 日次のクロール数・インデックス数・被リンク数。2026-11-27 は181日分返った
  - 日付は `/Date(ミリ秒)/` の形で、UTC の0時（ずれの書き込みなし）。そのまま UTC の日付にする（2026-11-27 確認）
- **使わないもの**: `GetUrlTrafficInfo`（実際には表示回数があるページにも 0 を返す）。
- **後回し**: `GetQueryStats`・`GetPageQueryStats` は未検証。確かめてから足す。
- **遡れない**: 日次で保存しないと消えていくため、最初に動かす。後から取り直せないので、API が返した1件ごとの内容をそのまま JSON の列にも残す（[database_design.md](database_design.md) の Bing テーブル）。
- **データの癖**: 曜日差が大きい（金・土が低い）。インデックス数はその日の在庫数で、合計してはいけない。

## 5. GA4 リアルタイム（貯めない）

リアルタイム画面（[overview.md](overview.md) §4）のデータ。画面を開いたときと「更新」ボタンを押したときだけ取り、自動では取り直さない。結果は DB の表に貯めない。

- **API**: GA4 Data API の `runRealtimeReport`。
- **対象**: 5サイト（LogiShift・TechShift・ConShift・FinShift・LeadHub）。1回の呼び出しで見られるのは1プロパティだけで、まとめて呼ぶ方法もない。プロパティごとに並行して呼び、API サーバーでまとめる。
- **認証**: 日次と同じ Google ログイン（§2）。
- **期間**: 直近30分まで（標準プロパティ。360 は60分）。今日の累計は出せない。
- **使える軸・指標**: 軸は15個だけ（国・市区町村・デバイス・イベント名・`minutesAgo`・`unifiedScreenName` など）。指標は PV（`screenPageViews`）・アクティブユーザー（`activeUsers`）・キーイベント（`keyEvents`）・イベント数（`eventCount`）の4つだけ。
  - 言語・ランディングページ・ページパス・流入元（参照元・メディア・チャネル）の軸はない。そのため除外設定（[api_design.md](api_design.md) §4）は使えず、どこから来たかも見られない。
  - `unifiedScreenName` は、Web ではページのタイトル（パスではない）。ページはタイトルで並べる。

**1回の更新での呼び出し**（サイトごとに6回）

| # | 軸 | 指標 | 画面に出すもの |
|---|---|---|---|
| 1 | なし | PV・アクティブユーザー・キーイベント | サイトごとの直近30分の値（数字のカード）。合計は画面で、選んだサイトから出す |
| 2 | `minutesAgo` | PV・アクティブユーザー | 分ごとの推移の折れ線（サイトごとに1本。PV とアクティブユーザーを画面で切り替える） |
| 3 | `unifiedScreenName` | PV・アクティブユーザー（PV の上位20） | 「いま見られているページ」の上位20（タイトル・サイト・PV・アクティブユーザー）。画面で選んだサイトの分をまとめて並べ直す |
| 4 | `deviceCategory` | アクティブユーザー（多い順） | デバイスの内訳（スマホ・PC・タブレット・その他）の帯グラフ。ユーザーの属性なので PV は取らない |
| 5 | `countryId` | アクティブユーザー（多い順に10） | 国の内訳の帯グラフ（ユーザーの属性なので PV は取らない）。画面で、選んだサイトで UU の多い3か国を出し、残りは「その他」にまとめる |
| 6 | `eventName` | イベント数（`eventCount`。多い順に20） | イベントの横棒グラフ。画面で、選んだサイトを合わせて回数の多い10件を出す |

- アクティブユーザーは、画面では「UU」と出す（[screen_design.md](screen_design.md) §3）。

- **上限**: リアルタイムの上限は、通常の API（日次バッチ）とは別枠。標準プロパティは、1プロパティあたり1日20万・1時間4万トークン、1プロジェクト×1プロパティあたり1時間1.4万トークン、同時に10件まで。公式の説明では、1回の呼び出しはたいてい10トークン以下。ボタンを押したときだけ取るので、上限には届かない。
- **数字の注意**（画面上部に注記の欄は置かない。2026-11-26 利用者の決定。国だけ、帯グラフの下に注記する）
  - ボットを含む数字。言語の軸がないので除外できない（LogiShift では日本語以外のユーザーが約3割。[api_design.md](api_design.md) §5.1）。日次の数字（除外あり）とは比べられない。
  - 主な指標は PV にする。Zaraz で GA4 を入れているサイトでは、アクティブユーザーが多めに出るおそれがある。Zaraz の `user_engagement`（ページを離れて約30分後に送られる）も数えるため（推測。未確認）。
  - 国は出すが、正確ではない。国の帯グラフの下に注記する。Zaraz への切り替え後、LogiShift では日本語ユーザーの PV の22%が米国と判定されている（[api_design.md](api_design.md) §5.2）。都道府県はリアルタイムの軸にないので出せない（2026-11-26 利用者の決定で国を足した）。
  - 取得した時刻（何時何分の数字か）を「更新」の横に出す。取り直すと変わる。
- **AI に渡す**: 「AI に聞く」ボタンで、表示中の結果を AI に渡せる（[ai_query_design.md](ai_query_design.md) §6.3）。

## 7. 作る前に確かめること（実装の最初にやる）

- GA4・GSC: 1日の行数
- GSC: LogiShift の1日分のクエリ×ページの行数が5万行に収まるか → 収まる（2026-11-27 に16ヶ月分を取り込んだ。5サイトで1日の最多は2,041行。取り込んだ数字は、Search Console の日ごとのクリック・表示回数・掲載順位と一致した）
- GA4: Google シグナルが有効か（有効だと件数の少ない行が隠される）
- GA4: プロパティのタイムゾーン
- GA4: ページタイトルの形（サイト名の付き方）と、同じパスに複数のタイトルが出る頻度
- Bing: `GetQueryStats` の中身（日付のタイムゾーンは確認済み。§4）
- リアルタイム: 1回の呼び出しのトークン数（`returnPropertyQuota` を付けると応答に出る）
